# Contribution Guidelines

Thanks for wanting to add something. This list is curated, not comprehensive — the bar is "a GTM operator would be glad they found this", not "it exists".

## Before you open a pull request

Read the rules below. Pull requests that ignore them get closed without much discussion, which is nobody's idea of fun.

## What belongs here

- **Claude Code skills, agents, plugins, and MCP servers** with a real go-to-market use case: prospecting, enrichment, CRM, positioning, messaging, content, lifecycle, paid, SEO/AEO, analytics.
- **Open-source repositories** that a GTM engineer can clone and run.
- **Official documentation** from the vendor or protocol maintainer.
- **Research** with a stated method and a reproducible result.
- **Courses, communities, and people** who teach this work publicly.

## What does not belong here

- **No SaaS vendor or agency links.** You may name any vendor in a description. Do not link to their marketing site. Open-source repository URLs are allowed, as are `genesysgrowth.com/tools/*` guide pages. This keeps the list from turning into a directory of landing pages, which is what happens to every list that permits vendor links.
- **Anything under 3 stars**, unless it is official (Anthropic, a protocol maintainer, or a first-party vendor MCP server).
- **Anything unmaintained** — no commits in 12 months — unless it is still the canonical reference for its topic.
- **Paywalled content** where the substance is behind the wall. A free article that mentions a paid course is fine. A signup form is not.
- **Anything you have not used.** "Looks interesting" is not curation.

## Entry format

One line per entry, in this shape:

```
- [Name](url) - Description that says what it actually does, who it is for, and what is specifically good about it.
```

Rules:

- **Descriptions are substantive, not slogans.** Say what the thing does, what it integrates with, and what a reader gets from it. Two or three sentences is normal here. One-liners like "A great tool for sales" get rejected.
- Start the description with a capital, end without a full stop only if it is a fragment. Be consistent with what is already there.
- No marketing adjectives. No "powerful", "seamless", "game-changing".
- Entries go in **alphabetical order** within their section. Not "most important first". Not "mine first".
- Link directly to the repository or doc. No tracking parameters, no shortened URLs, no redirects.

## Adding a new section

Open an issue first. Sections are structural and a badly-placed one is worse than a missing one. Say what the section is for and name at least five entries that would live in it.

## Quality bar

Every pull request is checked against:

1. Does the link resolve?
2. Is it maintained?
3. Is the description honest and specific?
4. Is it in the right section, in alphabetical order?
5. Would a GTM operator actually use this?

If you are adding your own project, say so in the pull request. That is not disqualifying and it is not held against you. Pretending otherwise is.

Open an issue. If something is dead, abandoned, or turned out to be bad, say so and it comes out. This applies to the maintainer's own entries too.
